# 1. Objective

Session 29 introduced the **PnL construction layer** for MXM V1.

The goal was to implement a deterministic mechanism that converts
`SessionResult` chains produced by the execution/backtesting layer into
economic **Profit and Loss (PnL)** observations.

This layer sits above execution and provides the first representation of
economic outcomes suitable for:

- strategy analysis
- reporting
- plotting
- attribution
- performance evaluation

A secondary objective was to run a **first real smoke script** that builds a
SyntheticAsset, runs a short historical backtest, and constructs PnL over the
result.

This smoke script serves as an **end-to-end debugger for the economic layer**.

# 3. PnL Decomposition Implemented

Session PnL is decomposed into two components.

## 3.1 Price-Move PnL

PnL generated by the mark-to-market change of carried positions.

```
price_move_pnl =
    initial_holdings × contract_multiplier × (mark_t − mark_{t−1})
```

## 3.2 Trade PnL

PnL generated by executing trades away from the session mark.

```
trade_pnl =
    realised_trades × contract_multiplier × (mark_t − fill_price)
```

## 3.3 Total PnL

```
total_pnl = price_move_pnl + trade_pnl
```

This decomposition isolates:

- exposure-driven PnL
- execution-quality PnL

# 4. Contract-Level PnL Support

During implementation an important design decision was made.

Instead of discarding contract-level detail during aggregation,
the constructor should retain it.

Future reporting and attribution layers will require:

```
PnL by contract
PnL by asset
PnL by signal
PnL by strategy
```

Therefore the constructor internally computes **contract-level contributions**
and aggregates them to the session level.

This preserves attribution capability.

# 11. Integration Failure Discovered

During backtest execution a timestamp mismatch occurred.

Error:

```
Cannot compare tz-naive and tz-aware datetime-like objects
```

Specifically:

```
KeyError: Timestamp('2025-01-02 00:00:00+0000', tz='UTC')
```

This revealed a deeper semantic issue.

# 12. Temporal Semantics Problem

The issue is **not merely timezone mismatch**.

The system is currently mixing two fundamentally different temporal concepts:

```
session labels
timestamps (instants)
```

## 12.1 Session Labels

Represent a trading session identity.

Example:

```
2025-01-02
```

Properties:

- not a moment in time
- not timezone aware
- label only

Current representation:

```
np.datetime64[D]
```

Used in:

- `TradingCalendar.trading_days`
- `ContractSeries`
- `ComponentWeights`
- `TargetHoldings`

## 12.2 Timestamps

Represent a precise instant in time.

Example:

```
2025-01-02 14:30:00 UTC
```

Representation:

```
pd.Timestamp (tz-aware)
```

Used for:

- order submission
- fills
- FX conversion
- market data timestamps

## 12.3 Category Confusion

Some components currently treat session labels as timestamps.

Example:

```
Backtester converting session → UTC timestamp
```

This causes slicing failures when used against session-indexed surfaces.

# 13. Correct Conceptual Model

Two temporal domains must be separated.

```
SessionLabel        → np.datetime64[D]
UTCInputTimestamp   → pd.Timestamp(tz="UTC")
```

Bridges between the domains must be explicit.

Examples:

```
SessionLabel → submission timestamp
Timestamp → session mapping
```

These bridges belong in the **execution layer**.

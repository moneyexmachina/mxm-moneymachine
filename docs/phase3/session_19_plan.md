# session_19_plan.md — MXM V1  
## Session 19 — Relative Contract Labelling & Identifier Layer

## Purpose

Session 19 introduces a **naming layer** on top of the deterministic contract
selection engine implemented in Session 18.

Session 18 resolves:

    (product_id, as_of_timestamp, selector_rule) -> contract_id

Session 19 defines:

    (selector_rule, as_of_timestamp, product_id)
        -> canonical_relative_id
        -> short_id
        -> label surface

The goal is to produce:

- **stable, machine-safe identifiers** (canonical)
- **ergonomic, human-readable identifiers** (short)
- without altering or polluting the core selection semantics

The selection engine remains unchanged.

## Design principle

> Identity resolution and naming are separate concerns.

Session 18 determines *which* contract is selected.  
Session 19 determines *how that selection intent is described*.

Naming must be:

- deterministic
- explicit
- independent of exchange string formats
- derived only from:
  - `PeriodFilter`
  - `SelectorRule`
  - selection semantics (LTD-based)

## Conceptual model

We introduce a **RelativeContractDescriptor** layer.

### 1. Canonical Relative Identifier

A fully explicit, machine-safe identifier that describes the selection intent.

Grammar (V1):

```
RC::<period_type>::<cycle_spec>::LTD::n=<n>
```

Examples:

- Front by LTD:
  ```
  RC::MONTH::NONE::LTD::n=1
  ```

- Second front:
  ```
  RC::MONTH::NONE::LTD::n=2
  ```

- December-only first eligible:
  ```
  RC::MONTH::CALENDAR_MONTHS[12]::LTD::n=1
  ```

Properties:

- Immutable
- Fully determined by `SelectorRule`
- Does not depend on `product_id`
- Does not depend on specific contract_id
- Stable across time

This becomes:

```
canonical_relative_id
```

### 2. Short Identifier

A human-readable ergonomic label.

Examples:

| Canonical                             | Short  |
|--------------------------------------|--------|
| MONTH / NONE / LTD / n=1            | LTD1   |
| MONTH / NONE / LTD / n=2            | LTD2   |
| MONTH / CALENDAR_MONTHS[12] / n=1   | Dec1   |

Properties:

- Context-dependent
- Potentially ambiguous across different period_types
- Not suitable for persistence
- Intended for CLI, logs, chart legends

Short IDs are:

- generated by a formatter
- never parsed for logic
- purely representational

### 3. Relative Contract Series Naming

When building a time series:

```
pd.Series(index=date, values=contract_id)
```

We attach metadata:

- `product_id`
- `canonical_relative_id`
- `short_id`

Example name:

```
cme_emini_snp500_futures::RC::MONTH::NONE::LTD::n=1
```

or for display:

```
ES:LTD1
```

## Scope of implementation

### In scope

1. **RelativeContractIdentifier module**

   - Function:
     ```
     canonical_relative_id(rule: SelectorRule) -> str
     short_id(rule: SelectorRule) -> str
     ```

   - Deterministic
   - No refdata access
   - No calendar dependency

2. **Formatter layer**

   - Maps canonical → short
   - Rule-based
   - Explicit (no guessing)

3. **SelectorRule augmentation**

   - Add method:
     ```
     rule.canonical_relative_id() -> str
     ```
   - Add method:
     ```
     rule.short_id() -> str
     ```

4. **Series metadata integration**

   Extend smoke script and/or helper to attach:

   ```
   series.attrs["canonical_relative_id"]
   series.attrs["short_id"]
   ```

5. **Unit tests**

   - Canonical ID stability
   - Short ID mapping
   - Round-trip serialisation safety
   - No accidental dependence on contract_id

## Explicit non-goals

Session 19 does NOT:

- change selection logic
- introduce calendar-based relative logic
- infer "next calendar month"
- introduce roll windows
- modify RefDataAPI
- introduce persistence

## Implementation plan

### Step 1 — Canonical grammar definition

- Formalise canonical ID string format
- Freeze grammar
- Add tests asserting exact string output

### Step 2 — Extend SelectorRule

Add:

```python
def canonical_relative_id(self) -> str
def short_id(self) -> str
```

Canonical built from:

- period_type.name
- cycle_elements
- rank key (LTD locked in V1)
- n

### Step 3 — Short ID rules

For V1:

If:

- period_type == MONTH
- cycle_elements is None
- rank == LTD

Then:

```
short_id = f"LTD{n}"
```

If:

- period_type == MONTH
- cycle_elements == {12}
- n == 1

Then:

```
short_id = "Dec1"
```

General form:

```
<ElementAbbrev><n>
```

Where:

- 1 → Jan
- 2 → Feb
- …
- 12 → Dec

Abbreviations must be deterministic and internal (no locale dependence).

### Step 4 — Series naming integration

Update smoke script:

- Replace current name surface with canonical ID
- Print both canonical and short

### Step 5 — Tests

Add `test_relative_ids.py`:

Test:

- MONTH / None / n=1
- MONTH / None / n=2
- MONTH / {12} / n=1
- MONTH / {3,6,9,12} / n=1 (should render canonical correctly)
- serialisation round-trip

## Acceptance criteria

Session 19 complete when:

1. Canonical IDs are deterministic and grammar-stable
2. Short IDs are explicit and documented
3. Selector engine remains unchanged
4. No selection semantics are inferred from labels
5. Series can expose stable metadata surfaces

## Outcome statement (target)

> “MXM V1 can now resolve contracts deterministically and attach stable, explicit relative identifiers describing the selection intent. Human-readable labels are layered cleanly above the engine without altering semantics.”

## Strategic impact

After Session 19:

- Synthetic assets can reference relative contracts by canonical ID
- Portfolio logic can key on canonical identifiers
- CLI and chart surfaces gain ergonomic labels
- Selection semantics remain minimal and composable

Session 19 builds directly and cleanly on Session 18.
